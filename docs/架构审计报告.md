## A. 正确性 Bug —— 会直接产生错误行为，优先修

### A1. 到期/逾期判定全线失效（严重 · 已实证）

**现象**：`reminders.due_at` 实际存储的是模型原样输出的中文自由文本，而到期判定按 ISO 时间戳字符串比较。

实测数据（`data/chat.db`，当前全部 3 条待办，**无一条是 ISO**）：

```
"10月6日 早上 8:30"    出发去近郊轻出行
"10月7日 晚上 22:30"   早点睡，调好生物钟迎接上班
"最后一天 22:30"       最后一天早点睡，把作息拨回工作日
```

**写入侧**（`server/llm/bailian.ts:269-272`）：`set_reminder` 把 `args.when` 原样入库，**无任何时间归一化**。

**读取侧**三处各自为政，且全部错误：

| 位置 | 判定方式 | 实测结果 |
|---|---|---|
| `server/db.ts:1252` | SQL `due_at <= now.toISOString()`（UTF-8 字节序比较） | 返回 **2 条**——含**尚未到期**的 `10月7日`；漏掉 `最后一天`（`最` 的 UTF-8 首字节 `0xE6` > `'2'`） |
| `server/scheduler.ts:93` | `new Date(r.due_at).getTime() <= ...` | `NaN <= x` → **恒 false** |
| `src/components/DashboardPanel.tsx:156` | `new Date(r.due_at).getTime() < Date.now()` | `NaN < x` → **恒 false**，"已逾期"徽章永不出现 |
| `src/utils/butler.ts:79` | `new Date(r.due_at).getTime()` | `NaN`，待办进度条数学失效 |

**净效果**：到期提醒**误报**（未来的也推）+ **漏报**（中文开头的永不推）+ 逾期态**永久不可见**。P1 刚做的主动能力有一半建立在这个坏地基上。

**改造方案**（推荐，单一真相源）✅ **已按此落地**：
1. `db.ts` 增加 `due_ts INTEGER`（真实 epoch ms，可空）；`due_at` 保留原文用于展示（本来就是文本列，无需另加 `due_text`，避免同义两列）。
2. 新增 `normalizeDue(raw, now)`：解析 `明天 9 点` / `每周一` / `10月7日 晚上 22:30` / `22:30` / ISO；解析失败则 `due_ts = NULL`、`due_text` 保留。
3. `addReminder` / `updateReminder` 写入时同时落两列。
4. `listDueReminders` 改为 `due_ts IS NOT NULL AND due_ts <= ?`。
5. `scheduler.ts:93`、`DashboardPanel:156`、`butler.ts:79` 统一改读 `due_ts`。
6. 一次性迁移脚本回填存量 3 条。

> 附：这是典型的"让模型输出直接进入判定链路"。同类风险点应在审计后统一收口——**模型自由文本 ≠ 结构化字段**。

### A2. 系统提示词的能力清单 ≠ 实际下发给模型的工具集（严重）

实测两处来源完全独立：

- **系统提示词**（`server/agent.ts:126`）：`enabledCapabilities()` → 读 `server/tools/index.ts:236` 的 `CAPABILITIES`
- **运行时 tools**（`server/llm/bailian.ts:591`）：`activeToolDefs(owner)` → 10 个 OpenAI function schema

差异矩阵：

| 工具 | 提示词清单 | 运行时 tools | 后果 |
|---|---|---|---|
| `open_artifact` | ❌ | ✅ | 提示词明写"**不要调用清单之外的工具**"，产物三件套全在清单外 |
| `create_artifact` | ❌ | ✅ | 同上——**这很可能是历史上"产物生成不稳定/模型编造内容"的根因** |
| `update_artifact` | ❌ | ✅ | 同上 |
| `recall_memory` | ✅ 恒定 | 条件（无记忆时隐藏） | 提示词与实况不符 |
| `get_schedule` | ✅ 恒定 | 条件（无待办时隐藏） | 同上 |
| `web_lookup` | ✅ 条件 | ✅ 条件 | 一致 |

**改造方案**：删掉提示词里对 `enabledCapabilities()` 的引用，改为注入 `activeToolDefs(owner).map(t => t.name)` 的**同一份**结果（在 `bailian.ts` 组装 messages 时计算，通过参数传给 `buildSystemPrompt`）。能力清单必须与 tools 数组**同源**，不允许两处维护。

## B. 架构层偏离 —— 不影响当下运行，但持续制造 Bug

### B1. 工具定义双份，且旧那份是死的（高）

`server/tools/index.ts` 保留了一整套 MCP 式工具构建器（`buildRecallMemory` 等 6 个 + `withRetry`），但**执行通道早已切到 `bailian.ts` 的直连 `execTool`**。当前 `tools/index.ts` 仅剩两个用途：
- `agent.ts:18` → `enabledCapabilities()`（即 A2 的错误来源）
- `bailian.ts:16` → 仅 `import type { ToolContext }`

`createSdkMcpServer()` / `buildXinglanServer()` 已是死代码。

**后果**：任何新增工具都面临"改一处还是两处"的歧义，且改错地方不报错——A2 就是这么产生的。

**改造方案** ✅ **已按此落地**：新建 `server/tools/registry.ts` 作为唯一注册表，
工具的 `name / description / parameters / enabled / timeoutMs / retries / run` **同处定义**；
`bailian.ts` 的 `activeToolDefs()` 与 `execTool()` 改为查表调用，删掉 263 行镜像实现；
`server/tools/index.ts` 整个删除（含 `createSdkMcpServer` / `buildXinglanServer` / `AGENT_PRINCIPLES`），
`@tencent-ai/agent-sdk` 依赖卸载。现在新增工具**只改一个文件**。

### B2. 活路径丢掉了容错（中高）

`server/tools/index.ts:50` 的 `withRetry(label, fn, max=3)` **只被旧 MCP 的 `web_lookup` 使用**（`tools/index.ts:191`）。
而真正跑的 `bailian.ts:245 execTool()`：**无 retry、无单工具超时**。
（`bailian.ts` 只为 `web_lookup` 特判了一次 dashscope 重试；`db` 写入类工具裸奔。）

**改造方案** ✅ **已随 B1 落地**：`execTool` 统一包 `withTimeout`（默认 15s，`web_lookup` 30s）+ `withRetry`（默认 2 次）。
错误**不抛**，以文本返回给模型让它自行改道；单个工具拖死整轮的问题也一并解决。

### B3. 实时变更通道空转（中）

`server/realtime.ts` 的 `notifyChanged()` → `subscribeChange()` → `/api/admin/stream`（`index.ts:748`）整条 SSE 链路，**前端引用数 = 0**（`src/` 全量检索无 `EventSource` / 无订阅）。后端每次数据变更都在推，无人接收；前端仍靠 `send()` 结束后手动 `refreshContext()`。

**改造方案**：二选一 ——
- (a) 接通：前端 `useServiceChat` 起一个 `EventSource('/api/admin/stream')`（需把路由移出 `/api/admin/` 或免鉴权），收到 `change` 就 refresh；
- (b) 删除：若单人自用、轮询足够，直接删掉 `realtime.ts` + `/api/admin/stream` + 所有 `notifyChanged()` 调用，减少认知负担。
> 建议 (a)：主动卡片/提醒到期本来就该实时到达，这是 P1 能力的最后一公里。

### B4. 模型供应商无运行时故障转移（中）

`resolveProvider()` 在请求开始前选定一家（DeepSeek 主 / 百炼备），流式过程中 `resp.status != 2xx` 直接 `throw`（`bailian.ts:396`），**不会自动切到备用供应商**。前端靠 6s 看门狗 + 本地兜底掩盖了这个问题，但那是降级不是容错。

**改造方案**：`streamCompat` 在**首个 chunk 之前**失败时重试备用 provider；已进入流式后失败则不重试（避免重复输出），仅上报。

### B5. 单体过大（中）

- `server/db.ts` 1,257 行 / 12 张表的 schema + 全部 CRUD 混在一起
- `server/index.ts` 797 行 / 50 个路由平铺
- `src/hooks/useServiceChat.ts` 的 `send` **单函数 408 行**：乐观更新、SSE 解析、工具事件、产物落库、看门狗、兜底 mock、错误分支全塞在一起
- `DashboardPanel.tsx` 619 行：记忆 / 待办 / 产物 / 版本历史 四个域

**改造方案**（按性价比排序）：
1. `send` 拆出 `parseSseStream()` + `applyEvent()` + `runFallback()` 三个纯函数（可单测），主流程降到 ~80 行。
2. `index.ts` 路由按域拆 `routes/{chat,memories,reminders,artifacts,proactive,admin}.ts`。
3. `db.ts` 拆 `db/schema.ts` + `db/{memories,reminders,artifacts,proactive}.ts`（保留 `db.ts` 做再导出，避免全量改 import）。
4. `DashboardPanel` 拆 4 个子面板组件。

**已落地（2026-10-06）**：四项全部拆完，行为不变，行数变化见顶部进度表。
拆分的硬要求与验证方式（后续再做同类拆分照抄）：
- **导出面先快照再拆**：`db.ts` 拆前把 65 个导出函数存成 JSON，拆后比对「缺失函数: 无」才敢删原文件。
- **路由零丢失**：遍历 `app._router.stack` 打印 `METHOD PATH`，确认 50 个路由、零重复。
- **纯函数抽到 `.ts`（非 `.tsx`）**：`src/components/dashboard/logic.ts` 可被 `scripts/*.ts` 探针直接 import（同 `chat-stream-probe` 做法），
  于是「重复检测 / 目标进度」这类带判定的逻辑有了 32 项回归，不再靠肉眼看 UI。
- **副作用外壳留父级**：`busy/notice/runOp` 收进 `useDashOps`，三个子面板共用一份，避免同一面板里出现两个互相打架的「操作中」。

**唯一有意的行为差异**：子面板的局部 UI 状态（搜索词、展开项、编辑草稿、版本历史）随 tab 切换重置。
原先这些状态挂在父级不随 tab 销毁，切回来会保留上次的筛选——属于无意识残留，重置更符合预期。
