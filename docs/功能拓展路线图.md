## 1. 界定前提

### 1.1 核心定位

**单用户、本地优先、对话驱动的「AI 生活管家」**。差异化不在"问答"，而在两点：

1. **被记住的感觉** —— 跨会话记忆、偏好沉淀、情绪追踪；
2. **不用你开口也替你盯着** —— 主动晨报 / 到期提醒 / 周复盘 / 关怀。

它不是客服工单系统，不是团队协作平台，也不是通用知识库。任何拓展都应服务于"更像一个记得你、懂分寸的管家"。

### 1.2 目标用户（现状推断 + 需你确认）

代码层面的硬证据：

- 前端 `useServiceChat` / `DashboardPanel` 中 `owner` **硬编码为 `'guest'`**；
- 全系统**没有任何用户鉴权**，`/api/*` 一律开放；只有 `/api/admin/*` 支持可选的 `ADMIN_TOKEN`（`server/adminAuth.ts`：未设置即放行）。

→ 结论：当前形态只支持**单人自用或单机演示**。这直接决定了"多用户 / 权限 / 多租户"类需求在现阶段 ROI 很低。

### 1.3 已有可复用能力（可直接调用，不必重造）

| 层 | 可复用资产 |
|---|---|
| 工具层（10 个） | `save_memory` `recall_memory` `get_schedule` `set_reminder` `create_artifact` `update_artifact` `open_artifact` `web_lookup` `checkin_mood` `ask_user` |
| 主动调度 | `server/scheduler.ts`：晨报 / 周复盘 / 到期提醒；已实现**记忆驱动选摘**、**免打扰时段**、**反馈学习闭环**（P1） |
| 人在环 | `ask_user` + `pending_questions` + 四种决策（approve / escalate / defer / cancel） |
| 记忆与提醒 | 完整 CRUD、过期清理、冲突检测、用户可编辑（P0） |
| 产物 | `artifacts` 表含 `version`，支持就地编辑、复制、跨会话列表 |
| 数据层 | SQLite 单文件（WAL + `busy_timeout=5000`）；表：`sessions` `messages` `memories` `reminders` `moods` `artifacts` `proactive_cards` `proactive_feedback` `pending_questions` `agent_runs` |
| 前端交互 | `XinglanShell` 三层结构（Rail / Stage / Overlay）、⌘K 命令面板、语音输入、明暗/强调色主题、Markdown 流式渲染 |
| 治理与自检 | `/api/admin/*`（画像 / 活动流 / 遥测 runs / 例外收件箱）；`/api/check-engine`、`/api/check-web` **已接入** `RuntimeSettings.tsx` |

### 1.4 关键约束

| 约束 | 现状 | 对拓展的影响 |
|---|---|---|
| 技术栈 | React 18 + TS + Vite 5 / Express + tsx / SQLite 单文件 | 适合快速迭代；不适合引入重依赖（向量库、消息队列） |
| 数据 | 单文件 SQLite，**无导出 / 无备份 / 无迁移**；单 owner | 数据资产有丢失风险；多用户需重构归属 |
| 外部依赖 | DeepSeek（主）+ 百炼（备，曾因欠费 Arrearage 不可用）；Tavily / 博查 联网 | 重度依赖 LLM 的功能（摘要、洞察）受配额与费用牵制 |
| 运行时 | 调度器随进程启动，**进程停则主动服务停**；60s 轮询 | "主动"能力依赖服务常驻，本地开发态下是间歇性的 |
| 人力 / 工期 | 从本会话看，P0、P1 各约一个工作台次完成 | 单功能建议控制在半天 ~ 1 天，走"小步快跑" |
| 已明确排除 | 外部通道（Webhook / SMTP 推送）——你已说"先不做" | 相关方向列入排除项 |
| 技术债 | `faqs`（27 条死数据）、`overrides`（只写不读）、CodeBuddy SDK 已移除、多 Agent 编排停用（`MULTI_AGENT=0`） | 清理属于低优先级维护，不是拓展方向 |

## 2. 拓展方向

> 每个功能点 = **解决什么问题** + **大致如何实现**。

### A. 功能增强（深化现有能力）

**A1 · 产物版本历史与回滚**
产物被就地编辑后会覆盖旧内容、无从找回；新增 `artifact_versions` 表，每次 `updateArtifact` 前快照旧内容，面板提供"历史版本"抽屉与一键回滚（复用现有 `version` 自增字段）。

**A2 · 记忆冲突一键合并**
当前只把重复记忆标成"可能重复"，仍需用户逐条手动删；在冲突徽标上增加"保留最完整的一条并合并其余"按钮，按信息量（value 长度 + 是否有过期时间）挑胜出者，其余调 `deleteMemory`。

**A3 · 待办子步骤与进度**
"帮我推进这件事"目前只产出一段文字，没有可追踪的分解结果；新增 `reminder_steps` 表（reminder_id / body / done）+ 工具 `add_reminder_steps`，目标卡内渲染勾选清单并按完成度驱动进度条。

**A4 · 主动卡内联可执行动作** ✅ 已落地（2026-10-06）
主动卡原来只有"接受/忽略"，接受仅标记 seen 不产生实际效果。现已给 `proactive_cards` 增加 `actions` 字段（JSON 结构化动作清单），并打通「服务端执行」与「客户端执行」两条分支：
- **服务端动作**（走 `POST /api/proactive/:id/action`，按卡片 `ref_id` 操作对应待办，带 owner 校验）：`complete` 完成打卡（→ `completeReminder`）、`snooze_hour` / `snooze_day` 顺延（→ `snoozeReminder`，周期提醒保留人类可读文案只移 `due_ts`）；成功后记一条 seen 反馈并收起卡片。
- **客户端动作**（不碰后端）：`ask_agent` 把预设问题丢给栖光对话（→ `dispatch`）、`open_view` 跳转到指定视图（→ `setView`）。
- **落点**：`XinglanShell` 在「此刻」视图底部浮起主动卡（`.xl-proactive`，冰青系统色、金留「人的环」），内联渲染四类动作；治理面板的「主动洞察」也对服务端动作直接开放（完成打卡 / 顺延）。
- 回归：`scripts/proactive-action-probe.ts`（18 项，覆盖 actions 往返、真实改写 DB、越权拒绝、客户端 clientOnly、周期保留文案）。

### B. 场景延伸（覆盖新业务场景）

**B1 · 跨会话连续性（会话摘要记忆）**
新建会话即失忆，之前的约定与结论带不过来；会话空闲/关闭时用 LLM 生成一段摘要存入 `session_summary` 表，新会话把最近 N 条摘要注入 system prompt（复用既有 `buildHistory` 的截断策略）。

**B2 · 周期 / 习惯型提醒**
提醒都是一次性的，"每天喝水、每周三开会"必须反复手动设；给 `reminders` 增加 `recurrence` 字段（daily / weekly / 星期位），完成或到期时由调度器自动生成下一实例（复用 `addReminder` 已有的语义去重防刷）。

**B3 · 情绪趋势洞察与低情绪关怀**
`moods` 只被用来算平均值，数据价值被浪费；新增趋势折线与"低情绪连续天数"判定，低情绪时主动语气转温柔并减少打扰强度（与既有 `buildMorning` 的 tone 分支衔接）。

**B4 · 基于自有内容的问答（轻量检索，非向量）**
用户想问"我之前那份行程里写了什么"时只能靠模型回忆；把 `artifacts` + `memories` 做成关键词检索（`tryFindArtifactContent` 已有模糊匹配基础），命中即注入真实内容，避免编造；**不引入向量依赖**。

### C. 集成与自动化（与外部系统 / 工作流打通）

**C1 · 数据导出、备份与恢复**
数据只存在于单个 SQLite 文件，误删即全丢；新增 `/api/export`（按 owner 导出 memories / reminders / artifacts / moods 为 JSON）与 `/api/import`，前端放在设置页一键下载。

**C2 · 日历订阅（ICS 导出）**
管家里的安排无法进入用户自己的日历 App；新增 `/api/calendar.ics`，把未完成提醒转成标准 VEVENT，用户可在系统日历中订阅（**无需任何第三方凭证**）。

**C3 · 本地文件 / 剪贴板导入生成产物**
想把一份已有文档交给管家处理时只能整段粘贴；支持拖拽文件到输入框，前端读取文本后走 `create_artifact` 落库，再让模型基于产物加工。

**C4 · 出站 Webhook（自动化钩子）**
想让管家事件（新提醒、待确认、晨报）驱动外部自动化（n8n / 企业微信机器人）；新增 `webhooks` 表 + 事件触发时 POST。**注意：此项与你"先不做外部通道"的决定冲突，需你确认是否解除。**

### D. 体验优化（交互方式与反馈机制）

**D1 · 流式 Markdown 增量渲染**
流式过程中为避免重复解析而直出纯文本，回答结束才渲染成 Markdown，观感上有一次明显跳变；改为分块增量渲染（仅对新到达的段落做解析），或在流式期用轻量行内格式化过渡。

**D2 · 主动卡"为什么推这个"+ 细粒度反馈**
用户不知道一张卡为何出现，且只能二选一地"看/划掉"，学习信号太粗；给卡片附 `reason`（触发它的记忆或提醒），并把反馈从 seen/dismissed 扩展为"有用 / 不感兴趣 / 太频繁"三档，喂给 `summarizeFeedback` 做更精细的克制策略。

**D3 · 窄屏 / 移动端适配**
现有断点（980px / 560px）只是让布局不塌，交互仍是桌面范式（右侧面板、悬浮层）；做一次移动端优先的布局收敛（单列 + 底部抽屉），保证手机上能用而非仅能看。

**D4 · 引擎与联网状态常驻可感知**
`/api/check-engine`、`/api/check-web` 已接入设置页，但只在打开设置时可见；把结果做成常驻状态指示（引擎在线/离线、当前 provider、联网可用性），失败时给出可点击的一键自检与引导。

### E. 形象与演出（栖光这个"人"的表现力）

**E1 · 形象演出编排** ✅ 已落地（2026-10-07）
`StarSprite` 定义了 8 种情绪，但此前 `XinglanShell` 只会机械派生 4 种（`waiting → thinking → speaking → calm`），`happy` / `concerned` / `sleeping` / `listening` 全是**死状态**——形象只是在跟随加载标志，从没真正"演出"过。现在补上导演层：

- **语气判读**（`src/utils/xinglanMood.ts` · `moodFromText`）：从助手回话读出 `happy` / `concerned`，读不出就 `null`（宁可不演，也不演错）。**硬约束：绝不产出 `waiting`**——暖金只属于「人的环 / 待你确认」，不能被一句疑问句稀释；`pendingQ` 才是 waiting 的唯一来源。负面词表整体优先于正面词表，因此「没能完成」判 `concerned` 而非 `happy`。
- **时间线编排**（`src/hooks/useXinglanPerformance.ts` · `decideMood`）：`waiting > listening > thinking > speaking > 送达定格 > sleeping > calm`。情绪只在**送达那一刻**定格（消息 id 变化 或 流式结束）并保持 4.2s 后自然回落；流式途中不判定（否则首句命中"完成"会把表情提前演掉且每帧抽搐）。空闲 75s → 安睡；精简模式不安睡（性能模式要的是"别动"，睡着更像卡住）。
- **氛围联动**：`.xc-wrap[data-mood]` 驱动光晕/星轨/环速，`MOOD_LABEL` 让「栖光 · xxx」跟着情绪走（静候 / 聆听中 / 思考中 / 诉说中 / 等你 / 为你高兴 / 有些在意 / 安睡）。开心仍用冰青——暖金纪律不变。

> ⚠️ 实现坑（已记入 memory）：`.xc-aura` 有常驻 keyframes，`opacity` 声明会被动画压过；要改氛围必须**整条替换 `animation`**，只写 `opacity` 是无效的。

- 回归：`scripts/xinglan-performance-probe.ts`（44 项，覆盖语气判读/负面优先/绝不产出 waiting/优先级裁决/8 种情绪全部可达/文案齐备）。

**E2 · 形象对"你"的记忆做出反应**
记忆条数、待办完成率目前只驱动仪表盘数字；让 presence 侧也感知（记忆丰度→环绕微粒，连续逾期→栖光主动"有些在意"），把形象从"状态显示器"变成"关系显示器"。

**E3 · 触摸/点击的物理反馈**
点击核心只有一次 `ping`；补按压回弹、长按唤出快捷动作、拖拽"把待办拖给栖光"，让形象有被触碰的手感。

### 推荐分阶段实施顺序（已按"自用 + 能力优先"重排）

**第一阶段 · 能力快赢（约 1~2 天，低风险）**
> A2 记忆一键合并 → C1 数据导出备份 → D2 可解释性 + 细粒度反馈 → D4 状态常驻

理由：A2 补完 P0 的"可干预"闭环；C1 在自用场景下是唯一副本的安全底线（成本极低）；D2/D4 复用既有端点。

**第二阶段 · 能力纵深主干（约 3~5 天）**
> A1 产物版本历史与回滚 → A3 待办子步骤 → B2 周期 / 习惯提醒 → A4 主动卡内联动作

理由：这四项把"记忆 / 待办 / 产物"三大资产从"能存"升级为"能演进、能追踪、能直接操作"，是自用体感提升的主干。A1 即既定里程碑 **P2 活产物** 的核心。

**第三阶段 · 智能化跃迁（约 1~2 周）**
> B1 跨会话连续性（P3）→ B3 情绪趋势洞察

理由：重 LLM、风险与成本最高，放在前两阶段稳定之后；先用少量样本验证摘要质量再放量。

**第四阶段 · 后置（能力站稳后再说）**
> C2 日历 ICS / C3 文件导入 / C4 Webhook / D1 流式渲染 / D3 移动端

## 4. 排除项（现有约束下不可行或 ROI 偏低）

| 排除方向 | 原因 |
|---|---|
| **外部通知通道（邮件 / 短信 / 微信推送）** | 你已明确"先不做"；且需要第三方凭证、送达率与反垃圾合规处理，与"本地优先、单人自用"的定位不匹配 |
| **完整多用户 / 鉴权 / 多租户** | ~~需权衡~~ → **已确认自用，永久排除**。当前 `owner` 硬编码 `'guest'`、全端点无鉴权，改造要动所有端点与数据表设计；自用场景下零收益 |
| **向量检索 / RAG 知识库** | 需引入 embedding 依赖或付费外部 API，与"单文件 SQLite、轻依赖"的技术约束冲突；且 `faqs` 27 条死数据已证明"预置知识库"路线在本产品价值有限（B4 的关键词检索是更划算的替代） |
| **多 Agent 编排** | `MULTI_AGENT=0` 已停用，原因是 4 次模型调用导致延迟过高；在"对话要即时、管家要轻量"的场景下不划算 |
| **移动端原生 App / 小程序** | 技术栈与交互范式均为桌面 Web，重做成本远高于 D3 的响应式收敛；除非确认必须移动使用 |
| **实时协作 / 共享记忆** | 强依赖多租户与鉴权（见第二条），前置不成立 |

> 另注：`faqs` / `overrides`（只写不读）属于技术债清理，不是拓展方向，建议低优先级顺手处理。

## 5. 仍然影响排期的关键信息（第 1 条已确认）

1. ~~**目标用户到底是谁？**~~ → **已确认：自用**。鉴权与多租户不再评估。
2. **是否需要手机端访问？** ——决定 D3 是"必做"还是"可延后"。
3. **模型预算与配额稳定性如何？** ——B1 会话摘要、B3 情绪洞察属重 LLM 功能，配额不稳会直接降级体验（历史上百炼曾因欠费中断）。
4. **人力与节奏？** 你一个人做还是有协作？每周能投入多少？——决定分期粒度是否要再切细。
5. **"先不做外部通道"是否解除？** ——决定 C4 Webhook 能否进入路线图；若解除，优先做哪种通道（邮件 / 微信 / 通用 Webhook）？
6. **部署方式？** 本地常驻还是部署上云？——调度器随进程运行，若非长期在线，所有"主动"能力都会打折，这会反过来影响 A4 / B2 的价值判断。
7. **数据隐私底线？** 能否接受把记忆 / 对话内容发给第三方服务（向量库、云端存储）？——决定 B4 是否只能走本地关键词路线。
