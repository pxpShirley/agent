## 1. 规格完整性（Spec Completeness）

### 1.1 已完整描述
- **视觉标识系统**（§3.3）：几何构造、状态变体、最小尺寸 24px、安全区，含可直接复用的 SVG。
- **拟人形象**（§4.1–4.4）：外观 SVG、5 性格、8 态情绪、情绪→表情映射、统一状态模型。
- **设计令牌总表**（§令牌）：24 个令牌齐全，取值与用途明确，且列为「唯一权威来源」。
- **响应式 / a11y / DoD**（§6–8）：断点、触控热区、对比度、reduced-motion、验收清单齐备。

### 1.2 不完整 / 缺失（影响功能迁移）
- **E1–E6 缺数据模型**：均停留在概念与「复用点」层面（如 E1「以星座呈现历史会话聚类」、E3「目标河流呈现 reminders 进度」），但**未给出**：① 渲染所需的数据结构（session 聚类字段、reminder 进度字段、milestone 快照结构）；② 该模块在三态中的精确布局落点（仅指向「挂载于三态之一」）；③ 新增组件/文件清单。
- **交互架构缺类型契约**：§5.1 称 EventBus 为「Typed 事件分发」、StateMachine 有「切换守卫」，但全文**未出现任何类型签名、转换表、守卫条件**。
- **13 事件缺 payload**：§5.5 仅列「触发时机 / 消费方示例」，无事件载荷结构（如 `confirm:open` 应包含 question / options / context；`agent:step` 应包含 stage / label / status）。无 payload 则 EventBus 无法真正实现「Typed」。

## 2. 依赖关系（Dependencies）

声明的复用关系正确（api.ts / useServiceChat / nebula.css / 三态范式），但存在**未对齐的依赖冲突**：

- **🔴 D1（核心歧义）EventBus 与 useServiceChat 共存方式未定义**：§1.3 把 `useServiceChat` 描述为「唯一聊天控制器」，§5.2 却写「chat:send 事件总线广播发送，useServiceChat 建会话」。两套叙事未说明：EventBus 是包裹 useServiceChat、还是替换其职责、还是仅用于副作用广播。这是架构级阻塞。
- **D2 现有 API 真实契约未附录**：文档只列端点路径（pill），未给出 method / 请求体 / 响应 JSON / 错误形态。迁移须以真实契约为准，否则前端字段映射靠猜。
- **D3 待改/待建文件清单缺失**：「XinglanCore 标识」「人的环」等未映射到具体组件（新建 vs 改写不明）；与现有 `PendingQuestion` / `ProactiveCard` 的替换关系未给出。
- **D4（歧义）E5「稍后提醒排程」后端依赖未定**：E5 称「仅扩展前端状态机、无新接口」，但「排程/稍后」隐含持久化，未说明刷新后是否仍需后端支持。

---

## 3. 接口定义（Interface Definitions）

- **现有接口**：9 个模块对应的 REST 端点仅以标签呈现，**无请求/响应 schema**，无法据此写调用层与类型。
- **新增事件接口**：13 类事件无 payload 类型、无返回值约定，Handler 注册表（§5.1 L4）无函数签名。
- **状态机接口**：具名状态 `home/memory/goals/loop` 已列，但**无转换表、无守卫实现、无与 `useServiceChat` 的集成点**。`state:change` 广播的承载字段未定义。
